This is C-only source inspection, not a measured detector benchmark or a biological result. The unchanged runner/owner can process196 genomes serially. Feasibility remains conditional on one actual complete full-method genome fitting the unchanged execution limits and on measured raw/archive/review costs. No new controller or scientific method change is needed.

Use `stage5_windows_backing_owner.py --accession <exact approved accession>` with one fresh owner spool per genome. Do not use its default FULL196 batch for the desired publish-after-each-genome route: that batch holds the original WorkflowLock across the queue, while the reviewed archive requires an unlocked `ONE_APPROVED_GENOME` result containing exactly one accession/result. Root's existing publication loop can select the next unfinished accession in the accepted panel order, launch this same owner, close it, archive/publish, and continue.

## Exact native schedule and source-sized work

The unchanged schedule is full PADLOC5027 HMMER search followed by native PADLOC classification, then each boundary-safe DefenseFinder task in sequence: full DefenseFinder family, full RM family, full Cas family, and unmodified native post-treatment. Tools use two threads/workers and the runner permits only two logical CPUs. No RM-only filtering, profile subset, omitted no-hit query or cross-genome target substitution is allowed. Initially, the compiled PADLOC database is read in place; it is not copied into each genome. Only an incomplete resumed query subset creates a bounded temporary database. DefenseFinder imports only matching complete profile evidence with the same target FAA/profile/threshold/HMMER identity.

Let D be the actual bundle's DefenseFinder task count: one combined gembase task for all multigene replicons when present, plus one ordered_replicon task per singleton; empty replicons remain review contexts. Fresh raw execution has `2 + 4*D` supervised top-level commands, plus MacSyFinder/HMMER descendants. Initial historical source-audit metadata for GCF_000009425.1 reports one replicon and2386 protein-bearing loci, so the expected first bundle is D=1 and six top-level commands; the actual source-validated bundle must confirm it. Historical configured family scope has1092/134/525 profiles; actual per-family scope records must confirm these counts. These are source/model records, not elapsed-time measurements.

The accepted pinned Stage3 summary contains398537 protein-bearing loci,2120 replicons and196 assemblies. PADLOC alone requires985292 per-genome profile query completions across the panel. Every genome has protein targets in the historical local audit, giving at least1176 top-level commands if each has one DF task; singleton tasks add four commands each. Historical source sizes range1177–3252 protein-bearing loci, with up to97 replicons in one assembly. Fragmented assemblies can therefore add substantial task/startup/review work. They must retain the same boundary-safe method.

No source-only runtime estimate is defensible. Pure arithmetic scenarios, excluding retries, provenance hashing, archive/publication and curation: a10-minute mean genome takes32h40m for196;30minutes takes98h;60minutes takes196h; four hours takes784h. The configured four-hour command and24-hour genome timeouts are failure bounds, not forecasts. First-genome timing should be followed by timings from subsequent full panel-order genomes; do not extrapolate one easy assembly as a guaranteed panel ETA.

## Continue or stop

Primary route: finish and independently review the first capacity02 full-method genome, archive/publish/reopen it, prepare its actual review queue, then continue one existing owner per unfinished approved genome. Pure C reading of immutable closed snapshots can be assigned in parallel to independent reviewers while later native genomes run. WSL curation prepare/apply/audit and archive operations must be serialized under the same ownership/resource/closure discipline; this document does not add an operational wrapper or authorize an unsupervised CLI.

Capacity02 requires2.375GiB guest MemAvailable before admission and before each native command, with unchanged1GiB guest reserve,3GiB Windows physical/commit admission,1.25GiB sampled descendant RSS stop and4GiB per-process address-space limit. The previously observed~2.42GiB guest headroom leaves only~46MiB above the guest admission threshold; provenance/bundle/cache activity can consume it. Passing initial admission cannot guarantee the next command is admitted. If it cannot fit or crosses the unchanged execution limit, preserve exact closure/checkpoints and use the already specified bounded host/WSL capacity revision with fresh gates; do not keep lowering bookings or parallelize native genomes.

Serial196 raw is not blocked by Stage4 or missing scientific execution code.
