# Stage5 setup resource failure closure correction

This is a source correction and fourteen passing synthetic contracts. It is not an actual successful setup, runtime discovery, storage mount, interoperability test, or detector run.

The actual `stage5_setup_diagnose_actual_postiq_01` attempt failed when Windows commit headroom measured 1,731,137,536 bytes, below the unchanged 1,879,048,192 byte setup threshold. Windows deactivated its lease; the Linux helper then reported `FAILED` with `Owner nonce/declared shared-lock ownership differs`. Supervisor construction failed before a native helper command. The old Linux terminal omitted the command count in that path. The old Windows exception handler waited for its own WSL client but omitted the retained terminal query and receipt. Its result correctly remained failed with unknown closure and a preserved STOP. Those original files remain unchanged; the new source does not retrofit them into accepted evidence.

The corrected Windows owner uses the same original WorkflowLock, resource threshold, lease, setup arguments and bounded native Supervisor. Any exception before Windows readback enters one failure finalizer. It deactivates the lease without requiring positive resource admission, waits at most fifteen seconds for the already retained WSL child, queries that retained handle, and saves `wsl_exit.json` before reading Linux evidence. Actual PID, creation/exit time, executable, session, exit code, argv, source hashes and stdout/stderr hashes are bound. An existing terminal receipt must match exactly. The saved terminal remains available even if subsequent Linux receipt checks fail.

The Linux helper initializes `owned_command_count: 0` and `no_native_launch: true` before constructing Supervisor, after current source and output checks. It records its actual argv, interpreter, boot ID and process birth. Finalization records current direct children; a failed child-list read or any surviving child makes closure unproven. Existing native command execution still supplies the real count and independently reopened launch/intent/command/closure/log receipts. No native receipt is invented for zero launches.

The Windows closure readback verifies exact nonce, scope, step, source, Linux argv, interpreter, boot and helper birth, empty direct children, native count/no-launch consistency, and terminal exit 2 for Linux `FAILED` or 0 for successful Linux setup. It reopens every actual native command receipt when present. Missing or mismatched evidence keeps closure unproven. A future exact system-interpreter preexec failure retains its existing narrow failed lane. The finalizer cannot turn a resource failure into setup PASS. When exact closure is proven, only the same unchanged nonce-bound STOP is removed. An uncertain Windows readback worker cannot be cleared using Linux closure alone.

Tests use temporary C files and synthetic retained-handle/child responses. They cover the failed-resource zero-launch receipt, exactly one fifteen-second wait, persistence of the actual client terminal before rejected nonce/source/argv/boot/child/count/intent/exit evidence, and a wait deadline retaining unknown closure. Eleven existing scope, bootstrap, filesystem and command evidence contracts also pass. No WSL, UNC, mount, G scientific payload or actual resource API was invoked by these tests.

Synchronous local filesystem/kernel calls are not claimed to have hard cancellation. If the owned WSL client does not close within the bounded wait, its identity cannot be checked, or Linux/native/Windows evidence is incomplete, STOP remains. The actual failed diagnose01 requires root's separately authorized reconciliation; a missing historical retained terminal is not reconstructed. Resource policy and any later WSL guest-cap change are separate decisions.
