## Native method and inputs

`stage5_atomic.py --config CONFIG run --accession ACCESSION --owner-lease LEASE --owner-nonce NONCE` admits exactly one accession from the SHA-pinned approved196 panel. Its separate output namespace is canonical `.work/stage05_atomic_v1/<accession>/`. A serial native guard and a per-genome guard prevent concurrent new runner owners; before a child starts, prior launches across this namespace must have retained actual closure receipts.

The runner reopens this genome's accepted source build receipt, every member hash and size, and its full196 source-validation certificate. It uses the preserved builder's `resume_one` and independent bundle auditor's `audit_one`; source coordinates, locus keys, sequences, replicon topology and native routing remain unchanged. PADLOC receives an assembly GFF with separate seqids; DefenseFinder routes multi-protein replicons through gembase and singleton replicons through ordered_replicon tasks. Empty replicons are explicit review states. No system may cross a replicon boundary; circular-origin adjacency remains an explicit native linear-search limitation.

Detection delegates to preserved `stage05_detectors.py::run_padloc/run_df`. Only its process execution, attempt allocation and closure callbacks are replaced. PADLOC2.0.0, its original R implementation, full5027 active DB2.0.0 profile scope, native HMMER searches and native classifier are retained. DefenseFinder3.0.0 uses actual MacSyFinder2.1.4 for all three upstream model families, retained native settings and unmodified DefenseFinder post-treatment. Native raw HMM/domain reports, all/best/rejected candidates, filtered extracts and pre/post-treatment tables remain available. Completion is independently parsed from raw query/footer/target statistics, including zero-hit profiles. A stopped run can reuse only complete, matching native query outputs; unfinished evidence stays retained and unverified.

This is a faithful invocation adapter rather than an alternative detector classifier. It uses MacSyFinder's upstream previous-run cache mechanism and PADLOC's existing-domtbl native path. The source adapters themselves remain locally constructed code, with exact SHA pins and source-interface tests; upstream releases do not certify this integration. Live retained-environment execution is required before operational adoption.

## Processes and resources

`stage5_work_storage.py` is a scoped proof helper, not a mount manager. Before the first job, the Windows lock owner must verify that the actual G target is empty and bind already available native ext4 `/var/tmp/lab_rm_stage05_atomic_v1` onto the exact Linux project `.work/stage05_atomic_v1`. The helper observes current mountinfo, boot, ext4 source block device/UUID, and the identical target/backing device plus inode; it rejects symlink paths, missing or duplicate exact mounts, nested mounts, a wrong filesystem and another backing directory. It reads 120 ext4 superblock bytes without a subprocess. `record` exclusively creates a new C-mounted proof file; it cannot mount, unmount, delete, signal or overwrite an existing proof.

The run config's `work_storage={proof_path,proof_sha256}` must bind that exact proof. The runner validates it before output creation, cache/closure adoption, every native launch and cache/final completion. Native launch configuration bindings and an invocation transaction retain the observed proof. Its helper SHA is a scientific implementation dependency; ephemeral proof SHA, mount IDs and boot are outside scientific identity so a verified remount/new-boot proof can resume unchanged science. `pin-runtime` can still run before storage proof creation. The owner must pin helper bytes and read Linux evidence through the derived Ubuntu UNC view, since Windows G and the Linux overlay expose different backing stores. No actual mount, UNC alias, ext4 UUID or live process behavior has been tested by these synthetic checks. See `stage5_io_scope_review.md` for the file-count basis and archive/restoration limits.

The caller must actually own the original stable Windows workflow lock and renew a fresh resource lease. The root-owned Windows owner accepts either the full196 queue or one exact approved `--accession` for bounded measurement/continuation; one selected genome never becomes full-panel completion. No shared owner or concurrent native worker policy is added. The Linux runner verifies nonce, age, physical/commit measurements, a nonempty mapping of actual Windows volume disk-free integer bytes, and a stable Windows owner PID plus creation time across renewals; the lease itself is not an independent Win32 lock probe. Admission requires every supplied Windows volume and the Linux output filesystem to meet the configured disk reserve. This prevents a large sparse WSL virtual-disk free-space reading from overriding an exhausted physical C or G volume. New Linux flock guards do not replace that lock.

Every native command uses a dedicated session, Linux subreaper, actual `/proc` birth identities and verified retained kernel pidfds. Kernel support is probed before launch; a prelaunch intent is persisted before `Popen`, and the root pidfd is retained immediately afterward before polling or filesystem reads. Only causal descendants or newly adopted children of this dedicated subreaper are discovered. Numeric PID/PGID membership alone never authorizes adoption or signalling. All signals use pidfds; unexpected PGID membership produces a fatal stop without signalling those processes. Actual root exit, group emptiness and tracked-descendant drain are required before command/genome success or retry admission. SIGTERM/SIGKILL cleanup is finite. A runner SIGKILL cannot write a closure receipt; that missing receipt or unmatched prelaunch intent blocks all later launches in this namespace until independently reconciled.

Resource admission has a finite maximum30-minute wait and explicit host physical/commit, Linux memory and disk reserves. Command/job deadlines are finite and at most24h; closure waits at most60s. Two permitted CPUs and two native workers are retained. RLIMIT_AS is inherited per process; sampled tree RSS provides a stop threshold. This draft does **not** provide an aggregate kernel memory cgroup cap or WSL VM-wide hard cap. Admission/runtime measurements and exact raw logs are retained separately from stable identity. Declared runtime/resource/interruption failures and closed nonzero native exits are retryable; provenance, unexpected source/receipt failures and unproved closure are fatal.

Four targeted Stage6 tree/join/dataset/hash negative gates passed under the bundled Python runtime. Separate curation V2 compatibility reports66 focused synthetic tests passed. These are preparation results, not actual native integration.

Hashing is streaming and conservative: full installed/model manifest verification is repeated per job, and unchanged retained native/audit helpers also reopen the ~984MB compiled PADLOC database. Repeated logical reads do not establish physical disk traffic: Linux page cache and the actual memory/workload determine that. Keep full verification for the first production genome and measure hashing wall/CPU time, actual I/O and memory pressure. If material, an independently verified read-only runtime shared within one owner batch could remove redundant model scans while preserving per-job input/cache verification and native query evidence. Read-only mounting by itself does not change these helper hash calls. No mutable mtime-only cache or forged verification shortcut has been introduced; optimization is optional, not a scientific completion gate. See `stage5_runtime_readonly_assessment.md` for the bounded source review.

TypeI/II(includingIIG)/III/IV classification and complete/partial/orphan architectures are intentionally absent from raw completion. In particular, native TypeI R/M calls do not prove an S component, generic MTases/HNH/VSPR do not prove complete R-M systems, and boundary/partial/annotation ambiguities require explicit downstream review.
